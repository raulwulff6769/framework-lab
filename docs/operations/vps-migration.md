# Перенос ITles/«Отсчёт» с Vercel на собственный VPS

Цель владельца: увести сайт + домены + БД с Vercel на свой VPS, чтобы работало в РФ без VPN.

- **VPS:** `161.120.186.182`, пользователь `agentuser` (есть sudo).
- **Провайдер:** Tencent Cloud CVM, регион **Сингапур** (AS132203) — это **не** материковый Китай, «Великого фаервола» тут нет.
- **База сейчас:** Neon Postgres (`neondb`, хост `ep-calm-hall-awak5tvl`), используется продом на Vercel.
- **Репозиторий-источник:** `raulwulff6769/framework-lab`, ветка `otschet-current`.

## Блокер входящего доступа (статус на 2026-09-28)

С Zo VPS **недостижим**: порты 22/80/443/2222 — silent timeout (пакеты дропаются, не reset).
При этом наш egress до `github.com:22` работает → режем **не мы**, дело во входящем фильтре на стороне VPS.

Локальный фаервол на VPS (по словам владельца) выключен (ufw/iptables off, sshd слушает `0.0.0.0:22`),
значит гейт — **Security Group в консоли Tencent Cloud** (по умолчанию deny-all на вход).

Что важно понимать:
1. **Ни я, ни владелец не открываем Security Group.** Из MCP у меня только Cloudflare (Workers/D1/KV/R2 — DNS и туннели там НЕ управляются) и Vercel; консоли/API Tencent нет. Владелец сообщил, что доступа в консоль Tencent у него сейчас тоже нет → путь «открыть 22/80/443 на вход» закрыт для нас обоих.
2. **egress-IP Zo плавающий:** `20.114.66.147 → 3.81.201.161 → 20.25.58.128` за одну сессию. Прописывать один /32 в SG бессмысленно — после ротации снова отвалится.
3. **Приложение уже умеет быть VPS-сервером.** `platform/dev/server.ts` в комментарии прямо помечен как «production server on a VPS (Node 20+, PostgreSQL через DATABASE_URL)»: один процесс = REST API + отдача статики SPA, порт из `PORT`, БД из `DATABASE_URL`, статика из `STATIC_DIR`. Отдельный шлюз/сборка не нужны.

### Решение: Cloudflare Tunnel (исходящий, БЕЗ единого открытого входящего порта)

**Основной путь.** Туннель инициирует сам VPS (egress у него работает) → Security Group обходится полностью, ничего открывать не надо. DNS домена `cloudflared` прописывает сам (проксируемый CNAME в зоне владельца) после одноразового `cloudflared tunnel login`. Мой Cloudflare-MCP это сделать не может (нет DNS/tunnel-инструментов), поэтому туннель поднимает владелец на VPS — пошаговым скриптом `docs/operations/vps-bootstrap.sh`.

## Шаг 0 — тест приёмника (READ-ONLY, запускается НА VPS)

Пока вход закрыт, готовность VPS проверяется скриптом, который владелец запускает у себя в SSH-сессии
и присылает вывод. Скрипт ничего не ставит и не меняет.

```bash
curl -fsSL https://raw.githubusercontent.com/raulwulff6769/framework-lab/otschet-current/docs/operations/vps-receiver-check.sh | bash
```

Показывает: ОС/железо (ядра, RAM, диск), sudo, уже установленные рантаймы (node/bun/nginx/caddy/psql…),
занятые порты, локальный фаервол, гео/провайдера, исходящую доступность (github/npm/cloudflare) и DNS.
Вывод даёт вердикт «приёмник-способен / чего не хватает».

## План миграции (две фазы, без входящих портов)

**Фаза A — сайт уже открывается с VPS, БД остаётся в Neon (нулевой риск для данных).**
Скрипт `docs/operations/vps-bootstrap.sh`, владелец запускает на VPS (пошагово, идемпотентно):
1. Node 20 + pnpm + git; клон `framework-lab@otschet-current` в `~/itles`.
2. Сборка SPA (`pnpm --dir platform build` → `dist`).
3. Единый процесс `dev/server.ts` как systemd-сервис `itles` на `127.0.0.1:8787`; `DATABASE_URL` = строка Neon (egress VPS→Neon работает — проверяется receiver-скриптом). Для точной копии прода задать те же секреты, что в Vercel: `GATEWAY_TOKEN` (обязателен — по нему стенд/шлюз авторизуется в API, 20 обращений в коде), `APP_SECRET` (подпись сессий/токенов), `CRON_SECRET` (для паритета). `SETUP_KEY` — как в проде.
4. `cloudflared`: `tunnel login → create → route dns ВАШ.ДОМЕН`, ingress → `http://127.0.0.1:8787`, `service install` (автозапуск). Домен открывается из РФ без VPN.
> В фазе A «базы Vercel» (Neon) остаются ЕДИНСТВЕННОЙ БД — все новые данные и так пишутся в Neon, зеркалировать нечего, миграции данных нет.

**Фаза B (опционально) — Postgres primary НА VPS + автозеркало новых данных в Neon.**
Только если владелец хочет саму БД физически на VPS. Тогда: локальный Postgres как primary, `DATABASE_URL` сервиса → localhost, и логическая репликация/CDC (или пуш-триггеры) новых записей в Neon. Это единственный этап с «копированием в базы Vercel», и он рискованнее фазы A (переносим данные) — согласуем отдельно.

**Vercel:** оставляем как запасной/зеркало; отключать деплой только после того, как домен с VPS стабилен.

### Альтернативы туннелю (если понадобятся)
- **Прямой Caddy/nginx + Let's Encrypt на 80/443** — только если владелец вернёт доступ в консоль Tencent и откроет входящие 80/443 (A-запись домена в Cloudflare → `161.120.186.182`). Тогда туннель не нужен.
- **Обратный SSH-туннель**, инициируемый VPS, — если Cloudflare по какой-то причине не подойдёт. Тоже полностью исходящий, вход не открывает.
