# Перенос ITles/«Отсчёт» с Vercel на собственный VPS

Цель владельца: увести сайт + домены + БД с Vercel на свой VPS, чтобы работало в РФ без VPN.

- **VPS:** `161.120.186.182`, пользователь `agentuser` (есть sudo).
- **Провайдер:** Tencent Cloud CVM, регион **Сингапур** (AS132203) — это **не** материковый Китай, «Великого фаервола» тут нет.
- **База сейчас:** Neon Postgres (`neondb`, хост `ep-calm-hall-awak5tvl`), используется продом на Vercel.
- **Репозиторий-источник:** `raulwulff6769/framework-lab`, ветка `otschet-current`.

## Блокер входящего доступа (статус на 2026-09-28)

С Zo VPS **недостижим**: порты 22/80/443/2222 — silent timeout (пакеты дропаются, не reset).
При этом наш egress до `github.com:22` работает → режем **не мы**, дело во входящем фильтре на стороне VPS.

Локальный фаервол на VPS (по словам владельца) выключен (ufw/iptables off, sshd слушает `0.0.0.0:22`),
значит гейт — **Security Group в консоли Tencent Cloud** (по умолчанию deny-all на вход).

Что важно понимать:
1. **Я не могу править Security Group.** Из MCP у меня только Cloudflare и Vercel — консоли/API Tencent нет. Правило добавляет владелец в веб-консоли Tencent.
2. **egress-IP Zo плавающий.** Записанный ранее `20.114.66.147` уже сменился на `3.81.201.161`. Прописывать один /32 нашего IP — ненадёжно (после ротации снова отвалится).

### Что владельцу добавить в Security Group (вход / Inbound)

| Протокол | Порт | Источник | Зачем |
|---|---|---|---|
| TCP | 22 | `0.0.0.0/0` (временно, ключ-only) | чтобы я мог зайти по SSH независимо от ротации egress |
| TCP | 80 | `0.0.0.0/0` | HTTP + выпуск сертификата Let's Encrypt |
| TCP | 443 | `0.0.0.0/0` | HTTPS-сайт |

SSH по паролю на 22/0.0.0.0/0 — рискованно; лучше ключ-only. Порт 22 можно после настройки
сузить/закрыть, оставив 80/443. Альтернатива, вообще не открывающая вход, — **обратный SSH-туннель**,
инициируемый самим VPS (у него исходящий интернет работает) — см. ниже.

## Шаг 0 — тест приёмника (READ-ONLY, запускается НА VPS)

Пока вход закрыт, готовность VPS проверяется скриптом, который владелец запускает у себя в SSH-сессии
и присылает вывод. Скрипт ничего не ставит и не меняет.

```bash
curl -fsSL https://raw.githubusercontent.com/raulwulff6769/framework-lab/otschet-current/docs/operations/vps-receiver-check.sh | bash
```

Показывает: ОС/железо (ядра, RAM, диск), sudo, уже установленные рантаймы (node/bun/nginx/caddy/psql…),
занятые порты, локальный фаервол, гео/провайдера, исходящую доступность (github/npm/cloudflare) и DNS.
Вывод даёт вердикт «приёмник-способен / чего не хватает».

## План после открытия доступа

1. **Рантайм:** Node 20+ (или Bun) на VPS; собрать SPA из `otschet-current` (`platform`), поднять Node-функцию `api/node.ts` как сервис.
2. **Реверс-прокси + TLS:** Caddy (авто-Let's Encrypt) или nginx+certbot; статика SPA + прокси `/api/*` на Node.
3. **DNS:** в Cloudflare (есть MCP) A-запись домена → `161.120.186.182`, прокси-оранжевое облако по вкусу.
4. **БД:** Postgres на VPS как primary; **автозеркалирование новых данных в Neon** (логическая репликация или пуш-триггер/CDC) — «базы Vercel» продолжают наполняться.
5. **Vercel:** оставить как запасной/зеркало либо отключить деплой после проверки.

## Фоллбэк без входящего доступа: обратный SSH-туннель (инициирует VPS)

Если владелец не хочет открывать вход, VPS сам поднимает туннель наружу к точке, куда Zo дотянется.
Это обходит Security Group полностью (исходящий у VPS работает). Детали согласуем, если пойдём этим путём.
