# ITles v2 — система, которая работает: моточасы, пробег, местоположение

Дата: 23.09.2026; ограниченный FLEX добавлен 24.09.2026. Документ описывает систему, собранную и проверенную в этом репозитории. Он заменяет разделы
«архитектура», «MVP» и «вопросы» из `DESIGN.md` (v1). Исследовательская часть v1 — классы техники, J1939,
законодательство — остаётся в силе с поправками из раздела 9.

Метки достоверности: **[измерено]** — получено прогоном кода или замером, артефакт указан;
**[первоисточник]** — документ производителя или ГОСТ; **[модель]** — симуляция с явными допущениями;
**[ограничение]** — предел физики или внешней системы.

## 1. Что изменилось после ответов заказчика

- Объём: три показателя ТЗ — моточасы, пробег, местоположение — для **любой** спецтехники в РФ,
  и всё, что из них следует: свежесть данных, история, наработка по дням, обслуживание по моточасам.
  Кубатура и 1С отложены (ответ на вопрос 15).
- Цена для клиента: сначала используем то, что уже есть в машине, покупка оборудования — в последнюю очередь.
- Продукт не требует имён, телефонов или почты водителей: вход — по логину от
  администратора организации. На этапе разработки используются синтетические
  данные; координаты реальной машины **могут** позволять идентифицировать человека.
  Перед пилотом нужен отдельный вывод о правовом режиме и месте хранения.
- Местоположение: главный администратор владельца техники отключает его для любой машины.
  После этого API не принимает координаты этой машины (ответ на вопрос 7).
  Офлайн-очередь шлюза пока может накопить точки до отправки: сквозной запрет сбора
  и поведение старого архива требуют отдельного решения до пилота. Если снова
  разрешить координаты до выгрузки, старые точки могут быть приняты ([план §3](../ROADMAP.md)).

## 2. «У спецтехники уже всё есть?» — как на самом деле в РФ

| Показатель | Что есть в машине по умолчанию | Как это достаётся без покупки оборудования |
|---|---|---|
| Моточасы | Счётчик на приборной панели есть у любой машины. У электронных двигателей (Common Rail, ЭБУ) то же число хранится в блоке управления: J1939 SPN 247 **[первоисточник]** | Фото или ввод показания с панели — эталон. Трекер с CAN читает ЭБУ автоматически. Телефон в кабине оценивает наработку между показаниями |
| Местоположение | ГНСС-терминал **обязателен** для лесозаготовительной техники и лесовозов с 01.01.2025 (ч. 1 ст. 96.3 ЛК РФ, данные через ГАИС «ЭРА-ГЛОНАСС» в ФГИС ЛК; письмо Рослесхоза от 02.11.2024 № ВС-04-29/27268) **[R2, R6]**. Амкодор ставит терминалы Galileosky с завода **[R6]**; ГНСС бортового компьютера у импортных харвестеров — опция **[R6]**. Для грузовиков с опасными грузами — АСН «ЭРА-ГЛОНАСС» (ПП РФ № 2216) | У такой машины трекер уже стоит, а у владельца почти всегда есть мониторинговая платформа. Подключаем её API или добавляем наш сервер вторым адресом в трекере |
| Пробег | CAN-одометр есть у грузовиков и части тракторов. У гусеничной и лесной техники его нет | Считаем по ГНСС устойчивым алгоритмом (раздел 5) по трекам любого источника |

Чего по умолчанию **нет**: канала связи от машины к нам. Облачные сервисы производителей (John Deere, Ponsse,
Komatsu Forest) ушли из РФ. Wialon Hosting отвечает `403` всем российским адресам **[измерено: 10/10 проб
Globalping в РФ, из Казахстана и Германии — не 403]**, поэтому российские парки работают на Wialon Local у интеграторов.

Итог. Покупать ничего не нужно, если в машине уже есть трекер, а у лесозаготовителей он обязателен.
Второй бесплатный вариант — телефон или планшет в кабине. Третий — показания счётчика по фото.
Трекер с CAN (от ~10 тыс. ₽) нужен только тому, кто хочет полностью автоматические точные моточасы
на машине без трекера.

## 3. Архитектура (реализовано)

```
Машина ─┬─ трекер (Galileosky / Навтелеком / Arnavi / Umka …) ──TCP: EGTS | Wialon IPS | Galileosky | FLEX*──┐
        │                                                                                         ▼
        ├─ платформа владельца (Wialon Local, Traccar, ISO 15143-3) ──API (2 клика)──┐   gateway/ (Python)
        │        └─ ретрансляция EGTS / Wialon Retranslator ──TCP──────────────────┼─► очередь SQLite ─HTTPS─┐
        ├─ телефон в кабине (PWA / Android) ──HTTPS, очередь IndexedDB───────────────┤                         │
        └─ показание счётчика (фото) ─────────────────────────────────────────────────┴──► platform/ API ◄────┘
                                                                                            PostgreSQL
   Кабинеты: веб (любой браузер), Android (APK), Windows (portable), iPhone/iPad (PWA)
```

- `platform/` — API (TypeScript, один обработчик `fetch(Request)`; проверен на Vercel и
  локальном Node/VPS, адаптер и деплой Cloudflare Workers здесь не проверены), PostgreSQL,
  веб-кабинет и лендинг (React + Tailwind), режим «Телефон в кабине».
- `gateway/` — TCP-шлюз для трекеров и ретрансляции. Только стандартная библиотека Python.
  Подтверждение устройству уходит **после** записи в очередь на диске. Запись удаляется из очереди только
  после подтверждения платформой. Записи неизвестных трекеров не теряются: они ждут регистрации до 60 суток.
  *FLEX-порт включается отдельно; реализован только ограниченный незашифрованный FLEX 1.0/2.0.
- `apps/desktop` — Windows (Electron), `apps/mobile` — Android/iOS (Capacitor), оба используют тот же интерфейс.

Модель данных — `platform/server/schema.ts`. Телеметрия хранится только дописыванием. Естественный ключ
`(источник, время[, показатель])` делает приём идемпотентным: повторно присланный архив не дублирует точки и не теряет их.

Роли: FUCHS видит всю сеть, дистрибьютор — своих клиентов, клиент — себя. Администратор организации
управляет пользователями по одноразовым кодам приглашения. Решения о местоположении принимает только
главный администратор владельца: переключатель на машине и «показывать ли координаты дистрибьютору и FUCHS».

## 4. Источники данных и подключение

| # | Источник | Подключение | Моточасы | Пробег | Стоимость |
|---|---|---|---|---|---|
| 1 | Платформа Wialon (Hosting/Local) | «Подключения» → войти в Wialon → токен только на чтение (`access_type=0x100`) → все машины появляются сами | счётчик `cneh` | `cnm` + наша одометрия | 0 |
| 2 | Traccar | адрес + токен | `hours` (мс → ч) | `odometer` + наша одометрия | 0 |
| 3 | ISO 15143-3 (AEMP 2.0) производителя | адрес Fleet + токен | `CumulativeOperatingHours` (ЭБУ) | `Distance` | 0 |
| 4 | Трекер в машине | IMEI на странице машины + наш сервер вторым адресом (`Serverip2` у Galileosky, сервер 2–3 у Навтелеком) | CAN (FMS, тег 0xDB) или счётчик трекера | CAN 0xC2 / ГНСС | 0 (трекер уже есть) |
| 5 | Телефон в кабине | «+ Телефон в кабине» → 6 цифр на телефоне | оценка по вибрации, калибруется по счётчику | ГНСС 1 Гц; при выключенном местоположении считается на телефоне | 0 |
| 6 | Показание счётчика | фото и число в кабинете или на телефоне | эталон | эталон (одометр) | 0 |

Важная деталь второго адреса **[первоисточник]**. У Galileosky (руководство ред. 0228) протокол один на оба сервера. Если основной сервер — ЭРА-ГЛОНАСС по EGTS, мы тоже получаем EGTS: координаты и пробег, а моточасы — только при привязке счётчика. Тогда моточасы берём из API платформы владельца или по показанию счётчика. У Навтелеком протокол задаётся для каждого сервера. Подробности — в `docs/research/factcheck-v2.md`.

Слияние: у каждого значения видны метод и время. Выбирается самое свежее точное значение. Оценка
показывается только если она новее, и всегда со знаком «≈». Показания счётчика задают сдвиг
относительных счётчиков, а для оценок телефона ещё и масштаб (`server/domain/counters.ts`).
Приоритет пробега: CAN-одометр → наша одометрия ГНСС → счётчик трекера или платформы.
Одометры трекеров на медленной технике в тестах ошибались на −57…+1138%.

**Сквозной прогон трекер → шлюз → платформа** (`scripts/gateway_e2e.py`, `docs/evidence/gateway-e2e.json`) **[измерено]**.
Реальный TCP от **имитатора машин**, 3 протокола, 3 машины, 3 дня **модельных данных**, зоны без связи с архивами:

| Харвестер / Galileosky | 957 → 957 | 0 | 3035,25 / 3035,265 (шаг SPN 247 — 0,05 ч) |
| Экскаватор / EGTS | 879 → 879 | 0 | 3065,1 / 3065,131 (шаг счётчика — 0,1 ч) |
| Лесовоз / Wialon IPS | 3589 → 3589 | 0 | 3026,75 / 3026,774 |

**Одометрия** (`scripts/odometry_validation.py`, `docs/evidence/odometry-validation.json`). Проверялся
рабочий TypeScript-код на треках симулятора **[модель]**, параметры подобраны перебором:

| Класс | Трекер по умолчанию | Рекомендуемая настройка | Наивное суммирование |
|---|---|---|---|
| Харвестер | −4,4% | +2,4% | +39…+282% |
| Форвардер | −4,5% | −4,8% | +8…+46% |
| Экскаватор (гусеницы, поворотная платформа) | +0,6% | −2,9% | +906…+7300% |
| Тракторы | −0,7% | −0,6% | 0…+1% |
| Самосвал, лесовоз | −0,3% | −0,3…−0,6% | 0…+1% |

Стоянка 12–72 ч на открытом небе, под пологом и под густым пологом, интервалы 1/30/300 с: ложный пробег
≤ 0,16 км (наивно — до 59,6 км). Копание на месте с поворотами платформы: 0 км. Перевозка на трале:
120 км учтены как «перевозка», не как пробег машины.

**Тесты на 23.09**: 13 тестов платформы (10 API и 3 анализа масла на PGlite; путь PostgreSQL дополнительно испытывался в предыдущем прогоне); 37 тестов Python, в том числе
декодеры шлюза на реальных пакетах устройств из набора тестов Traccar (Galileosky, EGTS, Wialon IPS, Wialon Retranslator);
UI-сценарий Playwright: первый запуск → организации → машина → код → телефон с эмуляцией ГНСС → данные в кабинете.

## 6. Ограничения реальности и чем они закрыты

| Ограничение | Почему оно есть | Решение в системе |
|---|---|---|
| В глубине леса или карьера нет сотовой связи **[ограничение]**; публичной статистики покрытия лесов нет | нет покрытия | Архив трекера (Galileosky 10 Plus — 170 000 записей; при долгом отсутствии связи старые затираются, поэтому производитель рекомендует microSD) или очередь телефона (IndexedDB). Досылка при выезде в сеть, для каждой машины видна свежесть. Для постоянного онлайна там — «Гонец-М» (тарифы через интеграторов) или LoRaWAN-шлюз на площадке (ГОСТ Р 71168-2023), см. фактчек §5 |
| 3G в РФ сворачивается (МТС — большая часть к концу 2026 г.) **[R5]** | решение операторов | Трекеры и телефоны с LTE и резервом 2G |
| Между точками трекера путь под пологом не наблюдаем **[ограничение]** | точка раз в 30–300 с, ошибка ГНСС 6–10 м | Устойчивая одометрия (±5% **на моделируемых** лесных маршрутах; поле ещё не сверено). Точнее потенциально — CAN-одометр или телефон (1 Гц, доплеровская скорость), если есть проверенный эталон |
| EGTS не стандартизует моточасы (`ABS_CNTR_DATA` — безымянный счётчик) **[первоисточник: ГОСТ 33472]** | стандарт | Номер счётчика задаётся для IMEI в настройках шлюза. Galileosky в режиме FMS даёт моточасы ЭБУ в теге 0xDB без настройки |
| Телефон не видит ЭБУ | нет доступа к шине | Показание счётчика — эталон, вибрация — оценка между показаниями. Оценка калибруется автоматически, её точность видна по расхождению со следующим показанием |
| iOS: нативная сборка требует Mac с Xcode и аккаунт Apple Developer **[ограничение платформы]** | правила Apple | На iPhone/iPad работает PWA («На экран Домой»); проект Capacitor готов к сборке на Mac |
| Vercel из РФ доступен ~70% сетей (21/30 проб Globalping; контроль ya.ru — 29/30) **[измерено]** | блокировки на части сетей | Разработка и демо — Vercel. Для продакшена тот же сервер (`platform/dev/server.ts`) запускается на российском VPS вместе со шлюзом |

## 7. Найдено при проверке у сторонних решений

- Traccar 6.15: EGTS-декодер отбрасывает `COUNTERS_DATA`/`ABS_CNTR_DATA`, моточасы теряются.
  Galileosky-декодер не разбирает тег 0xDB (моточасы FMS). Результат авторизации EGTS отправляется
  с кодом подзаписи 7, а по ГОСТ 33472 `EGTS_SR_RESULT_CODE` = 9. Всё это исправлено в нашем шлюзе и покрыто тестами.
- Гипотеза H-GS-1 из v1 закрыта первоисточником (протокол НПО «ГалилеоСкай», с. 15–16):
  CAN_B0 (0xC2) — пробег, значение × 5 = м; **моточасы — тег 0xDB, значение / 100 = ч**, а не CAN_B1.

## 8. Хостинг и что нужно от заказчика

На **23.09.2026** проект `itles` уже развёрнут на Vercel: канонический домен
`https://itles.vercel.app` и `/api/health` отвечали HTTP 200; БД ответила через
драйвер PostgreSQL (`db=pg`), первичная настройка завершена. В настройках есть
`DATABASE_URL`, `SETUP_KEY`, `APP_SECRET`, `GATEWAY_TOKEN`, `CRON_SECRET` (проверены
только **имена**, не значения). История связывает БД с Neon; свежий health не
устанавливает её версию или регион. Сборка `pnpm build:vercel` формирует
Build Output API v3. Последний production deployment `READY` от 12:28 UTC
не содержит Git SHA; утверждать, что там опубликован нынешний `main`, нельзя.

Предстоит с разрешения владельца связать **существующий** Vercel-проект с выбранным
рабочим `somemateria/biildfe4`, проверить изолированный Preview и привязать деплой к SHA.
Прежняя копия `clutteredcal/ITles` по-прежнему хранит бинарные релизы v0.3.0.
TCP-шлюзу нужен отдельный сервер с публичным адресом и управляемым доступом:
Vercel принимает HTTP, не входящие TCP-соединения трекеров. Затраты на VPS
уточнять по выбранному оператору и требованиям к данным, не по старой оценке.
Граница действий и безопасный порядок — в [`docs/operations/vercel.md`](../operations/vercel.md).

**Вопрос 8 (1С и лаборатория) и «гарантия 100%».** Честный ответ: гарантию, что интеграция заработает
в конкретной 1С без багов, заранее дать нельзя. Конфигурации дистрибьюторов (УТ 11, ERP, КА, УНФ) почти
всегда доработаны, и формат их данных неизвестен, пока нет доступа к копии базы. Гарантировать можно
способ: обмен через стандартные механизмы 1С (REST-интерфейс OData типовых конфигураций или формат

## 11. Масло (v2.1, 23.09.2026)

Для FUCHS главное — масло: его количество и состояние. Показатели (`platform/server/domain/sensors.ts`):
уровень %, «ниже минимума», давление, температура масла и гидравлики, вода (aw, ppm), вязкость,
диэлектрическая проницаемость, ферромагнитные частицы. Анализ считает доливы (скачок ≥ 5 п.п. на
медиане из 5 точек) и расход в % на 100 моточасов. Расход — это наклон регрессии уровня по моточасам
на отрезках между доливами. Проверено тестами: точные данные дают 30,000 из 30; при шуме ±1,5 п.п.
ошибка ≤ 10 %, ложных доливов нет; в проде через три протокола — 30,0 / 30,4 / 30,7 из 30 и 45,3 из 45.

| Датчик заказчика | Что это на самом деле [R8] | Как подключается |
|---|---|---|
| СУЖ М12 (СКБ «Индукция») | термисторный **сигнализатор** уровня с токовым выходом (≈35 мА в воздухе, ≈45 мА в жидкости, питание 12–18 В), не датчик процентов | через шунт на аналоговый вход трекера, порог в шлюзе (`threshold`, `when: below`) → `oil_level_low`; схему согласовать с производителем |
| Poseidon Trident QW/QM3100 | состояние масла (спектр импеданса), вода, температура; J1939 и Modbus RTU; американская компания — поставки в РФ не найдены | RS-485 (Modbus) или CAN трекера. Аналоги: Kongter OMS-300 (частицы, вода, вязкость; Modbus), MOP301 (вода aw/ppm; Modbus), Tianyi Q-1624 (старение по диэлектрику; J1939 и Modbus) |
| Rochester T-LL415 | ёмкостный датчик уровня 0–100 % ±5 % и температуры; только J1939, PGN/SPN не опубликованы | CAN трекера (сканер PGN), номера PGN/SPN — из документации производителя при закупке |

Без новых датчиков: электронные двигатели обычно уже передают по J1939 уровень (SPN 98), давление
(SPN 100) и температуру масла (SPN 175), гидравлика — SPN 1638. Трекер с CAN читает их. В шлюзе
значение датчика задаётся в `Mapping.sensors`: параметр Wialon IPS/ретранслятора (аналоговые входы там —
`adc1…adcN`), тег Galileosky (бит дискретного входа, таблица тарировки мВ → %, порог, пользовательские теги
0xE2–0xE9 с целым или IEEE-754 float) или аналоговый вход EGTS (ГОСТ 33472, Б.13).

Modbus-датчики состояния масла: у Навтелеком Modbus Master встроен (функции 0x01–0x04, до 32 параметров,
в т. ч. float), но прибор отдаёт только FLEX и EGTS, а значения Modbus лежат в пользовательских полях FLEX
(№ 207 и далее, FLEX 3.0). Текущий приёмник разбирает только базовые поля FLEX 1.0/2.0;
Modbus-масло по этому пути **пока не поступает**. Для расширения нужен стенд с атрибутированными
пакетами и сверка со спецификацией и декодером Traccar `NavisProtocolDecoder`.
Galileosky читает Modbus через загружаемый алгоритм обмена RS-485 и кладёт значения в теги 0xE2–0xE9.
Шлюз их уже разбирает. Источники: `docs/research/oil-sensors.md`.

## 13. Навтелеком FLEX: восстановленный ограниченный приём

Незавершённая прежняя реализация не была опубликована. В этой версии приёмник
написан заново по [спецификации производителя v6.2](https://downloads.navtelecom.ru/documentation/protocol/EN_Protocol_of_exchange_information_exchange_v6.2_070922.pdf)
(§1 и Annex A/B); размеры полей сверены также с Traccar 6.15.3
`NavisProtocolDecoder`. Набор `tests/data/navtelecom_vectors.json` содержит только
**опубликованные производителем примеры**, не захват с установленного устройства.
Отдельный кодировщик в `sim/protocols/navtelecom.py` и проверки TCP/очереди/API
используют **синтетическую** технику. Это не полевое испытание.

Реализованы вход по NTCB `@NTC`, согласование FLEX 1.0/2.0 и запрос снижения
3.0 до 2.0, сообщения `~A/~T/~C/~E/~X`, CRC, ACK после записи в SQLite. Поле 67
даёт CAN-моточасы, 37 — запасной счётчик от датчика работы генератора; поле 57
даёт CAN-пробег, 15 — ГНСС-пробег; время события и время последней валидной
фиксации сохраняются отдельно. Для счётчиков требуется поле 3 (время события)
в маске; кадр со счётчиками и нулевым временем события не получает ACK:
архив может застрять, а исправление часов не датирует старые кадры. Для них
потребуется отдельное решение. Чисто координатная запись с валидным временем
фиксации принимается. Дополнительные поля с картами водителя пропускаются.
**Не реализованы** пользовательские поля FLEX 3.0 для Modbus-масла, зашифрованный
транспорт, настраиваемая преамбула и телеметрия старого NTCB без FLEX. Ни один
реальный терминал или машина не проверялись; перед пилотом также требуется
сквозная политика отключения координат ([ROADMAP §3](../ROADMAP.md)).
