# ITles: состояние и план доведения до эксплуатации

Срез кода: **24.09.2026 UTC**; строки «Продакшен 24.09» и «Живой стенд 24.09» проверены
в этот день, остальные наблюдения о production и MCP относятся к 23.09. Это рабочий план, а не обещание пригодности для каждого
экземпляра машины. Архитектура и исходные допущения — в [DESIGN-v2](design/DESIGN-v2.md),
история решений — в [обзоре восстановления](research/project-history.md),

## 1. Зачем и для кого

FUCHS, дистрибьютор и владелец должны дистанционно видеть **моточасы, пробег и
местоположение** спецтехники в лесу, поле и карьере, время последнего обновления,
историю и обслуживание. Три показателя — базовое ТЗ; **масло — текущий приоритет
FUCHS**, для него уже есть приём/аналитика/интерфейс, но ещё нет проверки
физического датчика. Русский интерфейс:
веб/Windows/Android, на iOS сейчас PWA. Способ подключения выбираем по конкретной
машине: уже установленный трекер или его платформа → телефон → показания счётчика;
дополнительное оборудование — только если первые пути не дают нужного качества.
Нет требования монтировать наш прибор или собирать имена, телефоны и почту водителей.
Главный администратор владельца может выключить приём координат машины.

«Любая спецтехника» означает **набор проверенных способов для разных классов машин**,
а не обещание получить любой параметр с любой закрытой CAN-шины. Без покрытия нет
живой передачи; архив имеет конечную ёмкость. Успех моделирования не даёт численной
вероятности безотказности на установленном оборудовании.

## 3. Порядок работ и критерии завершения

Этапы идут по зависимостям, а не по неподтверждённым срокам. «Сделано» означает
артефакт проверки и принятие владельцем соответствующего решения.

### P0 — проверить публичные данные и восстановить релизный процесс

1. **Аудировать уже опубликованный импорт.** PR #1 слит в публичную ветку
   по умолчанию, но адрес старого релиза `clutteredcal/ITles` остаётся отдельным
   от адреса новых исходников. Проверить происхождение и право публикации
   скриншотов с машиной/координатами, Excel-книги, контактов в документации,
   адресов авторов и attribution trailers в истории. Часть значений могла
   быть модельной — это нужно доказать для *каждого* файла. Согласовать с
   владельцем обезличивание или удаление; если необходима очистка **истории**,
   объяснить её последствия для публичных SHA, PR и кэшей до любого
   force-push. Приёмка: реестр проверенных артефактов с разрешениями и
   отсутствие неподтверждённых данных в публичном состоянии и доступной истории.
2. Восстановить `.github/workflows/ci.yml` (Python, typecheck,
   Vitest, сборка Vercel), посмотреть реальный результат PR и права Actions.
   Подготовленный ранее файл **не входит в текущий checkout**: GitHub отклонил
   его публикацию токеном GitHub App без разрешения `workflows`. После выдачи
   права добавить CI отдельным изменением и
   подтвердить проверки на GitHub.
   Пока CI не опубликован, локальные тесты не выдавать за GitHub checks.
   Блоки этого плана можно переносить в issues с владельцем и критерием
   приёмки; не копировать туда сырые чаты/секреты. Приёмка: проверки
   опубликованного SHA разобраны; создание новых релизов и изменение
   ветки по умолчанию требуют отдельного согласованного процесса.
   Затем закрыть пробелы CI: `pnpm --dir platform e2e` и `scripts/gateway_e2e.py`
   пока не запускаются в jobs, поэтому зелёный CI не проверит сквозные пути.
   Добавить их с изолированными синтетическими данными и проверить на PR.
   Зафиксировать Python-зависимости через lock/constraints вместо диапазонов в
   `requirements.txt` и проверить установку в чистой среде; локальная проверка
   `pnpm --dir platform install --frozen-lockfile` повторно использовала установленные пакеты.
   Для **следующего** Windows-релиза устранить разрыв сборки: опубликованный
   `ITles-Windows-x64.zip` существует, но `apps/desktop` сейчас собирает NSIS,
   не переносимый ZIP. Зафиксировать способ упаковки ZIP/контрольные суммы и
   проверить запуск на Windows до выпуска нового бинарника.
3. **Ротировать действующие реквизиты**, если они совпадают с переданными в
   архивном чате (Neon и доступ к приложению); новые значения хранить только
   в предназначенном хранилище/Vercel, не в Git и не в issue. Действие требует
   владельца секрета и осторожной смены без простоя. Приёмка: старые реквизиты
   отозваны, staging/production health после смены 200, секретов нет в diff.

### P1 — воспроизводимое развертывание и безопасный сбор данных

4. В **существующем** Vercel-проекте `itles` связать правильный GitHub-репозиторий,
   использовать фактическую ветку по умолчанию `hoplite/ambrakia-ef0998c9`
   (либо отдельно согласованную новую базу), код приложения — из `platform/`; сверить
   `pnpm build:vercel` и Build Output API v3, настройки runtime, SSO preview,
   cron и области применения переменных. Сначала изолированный preview со
   **синтетическими** данными и резервная копия БД, затем — с согласия владельца —
   production и запись Git SHA в журнал деплоя. Это не повод создавать второй
   проект `itles`. Подробности — [runbook](operations/vercel.md).
5. Для TCP-шлюза выбрать контролируемый сервер с публичным адресом (предпочтительно
   подходящий регион РФ), TLS на исходящем API, ограничить входящие порты,
   защитить SQLite-очередь/ключи, мониторить глубину очереди, отказы, повторные
   отправки и истечение архива устройств. Проверить неизвестный IMEI, подмену
   источника и повтор пакета. **Не открывать шлюз для реальных трекеров** только
   по результатам симуляции. Приёмка: воспроизводимый деплой, восстановление из
   резервной копии и прогоны отказов с сырыми обезличенными трейсами.
   Отключение координат сейчас действует при приёме в API, но шлюз до отправки
   сохраняет декодированные записи в SQLite, в том числе в офлайне. Если
   координаты снова включить до выгрузки очереди, прежние точки будут приняты.
   Права файлов 0600 ограничивают доступ обычных локальных пользователей,
   **но не выполняют запрет сбора координат на шлюзе**. Перед пилотом
   согласовать поведение очереди при отключении координат и недоступном API;
   реализовать доставку политики до шлюза с проверяемым безопасным поведением
   при потере связи и тестами.
6. **Частично выполнено в этом изменении:** NTCB-вход, согласование FLEX 1.0/2.0,
   CRC/длины и маска полей, время события и координат, архивы и ACK после записи
   в очередь; примеры производителя с происхождением и отдельный кодировщик
   синтетической модели. Добавлена четвёртая машина FLEX в `scripts/gateway_e2e.py`.
   Сверены спецификация v6.2 и ширины полей с Traccar 6.15.3; публичные тестовые
   захваты Traccar с неустановленным происхождением ID/координат **не включались**
   в Git. Следующий шаг — атрибутированные обезличенные пакеты с изолированного
   реального терминала, проверка обрывов, согласования версий/15-значного ID
   и взаимодействия с его архивом. Счётчики без валидного времени события не
   датируются: маска без поля 3 отклоняется, кадр со счётчиками и нулевым временем
   отклоняется **без ACK**, поэтому может блокировать архив до устранения проблемы
   часов и согласованной ручной обработки ранее записанных пакетов: исправление
   RTC задним числом не создаёт время события. Проверить часы терминала до подключения;
   затем отдельно FLEX 3.0 и пользовательские поля 207+ для Modbus-масла.
   Эту реализацию нельзя считать подтверждённой совместимостью с устройством
   или проверкой датчика масла. EGTS остаётся вариантом для совместимого терминала.

### P1 — стенд с оборудованием и ограниченный пилот

7. Составить для 5–10 реальных машин матрицу «модель/год/ЭБУ → установленный
   трекер/платформа → разрешённый канал → ожидаемые показатели и метод/единицы».
   Владелец или интегратор предоставляет **тестовый доступ**, модель и разрешение
   на работу с CAN; не публиковать IMEI, координаты и учётные данные. До покупки
   попробовать API существующей платформы, ретрансляцию/второй сервер (учитывая
   одинаковый протокол двух серверов Galileosky), телефон и фото панели.
8. На изолированном стенде сначала состыковать реальный трекер с CAN-эмулятором
   (J1939/SPN 247, CAN-одометр, выбранные масляные SPN), захватить пакеты и
   досылку после отключения связи. Для приоритетного сценария FUCHS здесь же
   проверить на стенде доступные масляные параметры/калибровку хотя бы одного
   выбранного устройства; P2 ниже — расширение каталога датчиков, **не**
   перенос всей функции масла на потом. Затем — по согласию владельца — на машине:
   пассивное чтение по умолчанию; активные PGN-запросы только после согласования
   гарантийных и электрических рисков. Независимо сверять моточасы с панелью,
   пробег с одометром/контрольным маршрутом, координаты с разрешённым эталоном,
   а масляные значения с паспортом и калибровкой датчика. Результат: протокол
   испытания **по каждой комбинации**, погрешность и неопределённость отдельно
   для CAN/API/ГНСС/телефона, список неподдерживаемых случаев и исправления.
9. Отдельно испытать 5–10 телефонов: Android с выключенным экраном и выгрузкой
   очереди после отсутствия сети, iOS PWA в реальных ограничениях ОС, согласие
   владельца на координаты и отключение записи на сервере. Нынешний веб-режим
   не заменяет нативный фоновый модуль; вибрационные моточасы показывать как
   **оценку**, до калибровки не как показание ЭБУ.

### P2 — промышленная надёжность и масштабирование

10. Договориться о проверяемых порогах **на конкретные источники**: допустимое
    расхождение с эталоном, максимальная задержка после возврата сети,
    длительность работы вне покрытия с учётом ёмкости архива, правила свежести,
    периоды хранения, RPO/RTO и процедура поддержки. Замерить нагрузку и число
    соединений к Neon, проверить миграции/backup/restore и аудит доступа; добавить
    мониторинг API, cron, gateway, очереди и внешней карты. Никакого обещания
    «99,9999%» без длительного полевого наблюдения и согласованной методики.
11. Для остальных датчиков масла по паспорту выбрать сигнал (уровень/порог/вода/
    состояние), интерфейс J1939/аналоговый/Modbus и размещение; bench/HIL →
    монтаж по согласованию → сравнение с независимым анализом. Не приравнивать
